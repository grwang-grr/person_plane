## 从源码确认的差异

1. 截图中的“浏览量”是 Views，应统一为“视图”；“循环”为 Cycles，统一为“周期”；“页”为 Pages，作为项目文档。
2. 当前源码的“更多”是扩展侧栏开关。导航来自 packages/constants/src/workspace.ts，当前动态项包括视图、分析和归档。仓库也存在活动周期等页面，应依据实际路由和展示配置核对，不能只读旧版 workspace-menu.tsx 的数组。
3. 不同项目显示不同入口，取决于 cycle_view、module_view、issue_views_view、page_view 等功能开关。必须保留项目级配置，不强制所有项目展示固定的十个菜单。
4. 当前本地 project-navigation.tsx 的基础菜单没有独立“概述”项，本地路由扫描也未找到与截图完全对应的项目概述页面。该项属于版本或功能差异待核对，不能称为已经找到的原版现成页面。
5. 用户此前新增的计划、里程碑、问题与风险等需求仍保留为扩展需求；应单独标记，不能混称为截图中已有的 Plane 原生模块。

## 当前工程差距

当前 wplane 已实现部分项目任务、草稿、便签和个人工作页面，但存在以下差距：

- 多数项目内模块仍是标题和空状态。
- 更多采用自定义快捷菜单，尚未复用原版扩展侧栏。
- 原版复杂筛选、布局、编辑器、拖拽、文档与归档等依赖没有完整移入。
- 当前个人工作任务列表也未覆盖原版全部布局和筛选行为。

因此，已完成的页面样式和基础 CRUD 不能作为本次全量范围已经完成的依据。

## 推荐复用方式

建议以 Plane 原版路由、页面组件、共享组件、编辑器、状态管理及相应服务接口为复用单位，再做个人模式适配。继续逐页重绘会重复实现大量关联行为，容易持续产生差异。

组织架构界面与内部工作空间实体应区分：可以隐藏组织、人员管理、多空间切换等界面，但原版路由、项目关系、活动、创建人、分配和订阅大量依赖工作空间与用户标识。可优先评估保留一个内部默认工作空间与一个本地用户上下文，免登录并不等于删除这些业务关联。

原版前端依赖的 API 与当前 FastAPI/SQLite 接口并不兼容。整体复用原版后端能保留更多业务逻辑，但会引入原架构的服务依赖；保留当前后端则需实施足够完整的接口与数据模型兼容层。原生 Windows 的运行约束必须纳入验证，尚未决定切换后端或删除现有数据。

## 验收方式

对每个入口建立“路由 → 子页 → 操作 → API → 数据保存”的清单。创建、编辑、取消、删除确认、刷新、返回、错误和空数据状态逐项验证。不能用标题页、禁用按钮、占位空态、固定统计或临时演示数据代替已完成的功能。

原版复用与个人模式适配应先验证一条完整链路：默认本地上下文 → 项目 → 工作项 → 编辑与详情 → 布局与筛选 → 保存并刷新；通过后扩展其他模块。迁移前保留当前代码与用户数据，避免覆盖已有成果。
